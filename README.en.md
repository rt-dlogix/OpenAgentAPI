# OAA (OpenAgentAPI)

> Turn the **AI desktop clients you've already logged into** on your computer into one unified **OpenAI-compatible API** — no extra cost, no reverse-engineering. Reuse the quota your accounts already come with.

---

## Why you need it

You probably have several AI clients installed at once: Qoder, Trae, ZCode (Zhipu GLM / Z.ai), WorkBuddy (Tencent CodeBuddy), CatPaw (Meituan Miaoshou), MiniMax Code, Mirasim… Some hand out free credits, some throw in memberships, some are great for coding, some excel at long-form writing. But they're all isolated — each with its own login session and its own client — and **can't be scheduled from one place**.

What OAA does is simple:

> **Read the credentials of the clients you've logged into locally → aggregate them into an account pool → expose it as a standard `/v1/chat/completions` endpoint.**

Then any OpenAI-compatible client you already use (Cherry Studio, Open WebUI, VS Code extensions, your own scripts…) can connect directly. Behind the scenes, OAA automatically picks an available account to forward to, based on **priority + health + 429 fallback**.

---

## What it does for you

- 🔌 **One entry point**: a single `base_url` for every OpenAI-compatible client — no more re-logging-in every time you switch tools.
- 🪪 **Zero-cost quota reuse**: it only reads the local login state of accounts you're already signed into. The quota comes from what your accounts already include — no cracking, no bypassing of any authentication.
- 🧠 **Smart multi-account scheduling**: the account pool routes by priority and health, and automatically falls back to the next available account on `429` / rate limiting, so continuous calls never break.
- 🖥️ **Desktop + IDE coverage**: automatically detects and harvests the accounts you're logged into across Qoder, Trae, ZCode, WorkBuddy, CatPaw, MiniMax Code, Mirasim, and more (desktop clients / IDE plugins) — collected one by one, pushed idempotently.
- 🛡️ **Safe by default**: the gateway is **fail-closed (refuses to forward)** until a key is created; credentials are stored in plaintext but enforced with `0600` permissions + atomic writes.
- 🐳 **One command to launch**: Docker one-shot deployment, with the admin panel and OpenAI-compatible endpoint isolated on separate ports.

```
┌─ Local machine (Windows / macOS / Linux · Node ≥ 20)────────┐
│  Each platform's client already logged in                    │
│        │ local decrypt (read-only)                            │
│        ▼                                                      │
│  OAA-local  harvest creds → local account store → push ──────┼──┐
└──────────────────────────────────────────────────────────────┘  │ POST /api/accounts
                                                                   ▼
┌─ Server / local gateway (Docker · Rust ≥ 1.88)───────────────┐
│  OAA-server  account pool · priority · 429 fallback · egress │
│                     │                                        │
│                     ▼  /v1/chat/completions                  │
│              any OpenAI-compatible client                     │
└──────────────────────────────────────────────────────────────┘
```

> **The server never initiates any login**: it only receives credentials already generated by your local machine. Multiple accounts are accumulated by "log in one → harvest → push", repeated in turn.

## Components

| Directory | Role | Stack | Description |
|---|---|---|---|
| `bin/` `src/` | **OAA-local** — local credential harvesting & pushing | Node ≥ 20 (zero third-party runtime deps) | Reads local client login state, saves to a local account store, pushes to the gateway |
| `OAA-server/` | **OAA-server** — aggregation & routing gateway | Rust ≥ 1.88 / Docker | Account pool, priority scheduling, OpenAI-compatible endpoint, admin panel |

The two components are **independent**: OAA-server can run on a server, while OAA-local must run on the machine that has the clients installed.

## Quick start

### 1. Launch the gateway (OAA-server)

```bash
cd OAA-server
docker compose up -d --build
```

Open `http://<host>:3066/` in a browser → register an admin → create a Key on the "Gateway Key" page.

> Two ports are used: `3066` is the panel (UI + `/api/*`, bound to loopback by default), `3065` is the gateway
> (`/v1/*` + `/health`, the only one you should expose). See "1.5 split-port deployment" in DEPLOY.md.

### 2. Harvest and push (OAA-local)

```bash
# Probe installed / logged-in clients on this machine
node OAA-local/bin/harvest.js detect

# Harvest the logged-in accounts on this machine and store them
node OAA-local/bin/harvest.js scan --save

# Dry run (only shows the request body that would be sent)
node OAA-local/bin/harvest.js push --dry-run

# Actually push
node OAA-local/bin/harvest.js push --endpoint http://127.0.0.1:3066 --key <gatewayKey>
```

### 3. Connect a client

Point your favorite OpenAI-compatible client's `base_url` at `http://<host>:3065/v1`,
and set `api_key` to the Key you created on the panel.

## Security & compliance

- This project **only reuses the local login state of your own accounts** — no cracking, no bypassing of any authentication; the quota comes from what your accounts already include.
- Forwarding that **reuses login state in a non-official-client form** may **violate upstream service terms**, and carries risks of rate limiting / risk control / account freezing. Assess and control your usage intensity at your own discretion.
- Credentials are **stored in plaintext on both ends** — never commit them to a public repo, upload them to cloud storage, or share them.
- Recommended: keep the gateway reachable only on the LAN / loopback; for cross-public-network access, use a TLS reverse proxy and restrict source IPs.
